## Purpose

Fix a design wart in the M1 pre-push gates. Both
`scripts/check_file_scope.py` (M1.4) and
`scripts/check_story_dependencies.py` (M1.3), when a `WAIVE_SCOPE` /
`WAIVE_DEPS` waiver is supplied, **append an audit line to the active
story spec(s) — tracked files — during the pre-push hook, i.e. *after*
the commit being pushed has already been created.** The push succeeds,
but the working tree is left dirty with an un-committed mutation of a
tracked file that is not part of any commit.

This has now bitten the project twice (the 3C.3 push and the 5787d2e
3C.8 closeout push), each leaving a modified spec behind. The mutation
is invisible to the pushed history, forces a follow-up "what do I do
with these lines?" decision, and — if the operator commits them in a
later unrelated change and pushes again — can re-trigger the same gate
and append *another* audit line (a waiver-write loop).

This was the item flagged on the M1 epic row as "M1.6 waiver-timing
refinement deferred"; this spec makes it concrete.

## Where this runs

**Local, CPU-only.** Pure tooling + test change; no model / data work.

## Scope contract (atomic story)

- **One question:** how should a documented pre-push waiver record its
  audit trail without mutating a tracked file after the pushed commit?
- **One artifact bundle:** the two gate scripts + their tests, updated so
  waiver audit trails are durable and reviewable but do **not** dirty
  tracked files post-push.
- **One acceptance check:** a waived push leaves the working tree clean
  (no tracked-file modification), and the waiver is still recorded in a
  durable, operator-reviewable location with a defined follow-up path.

## Candidate approaches (decide on promotion to `todo`)

1. **Separate generated/untracked audit log (preferred default).** Write
   waiver records to a gitignored append-only log (e.g.
   `.git/waiver-audit.log` or a gitignored `docs/audit/waivers.log`)
   instead of the spec file. Add an explicit follow-up workflow: a small
   `scripts/` helper (or a documented manual step) that lets the operator
   review the log and, if they choose, fold the relevant entries into the
   spec's `## Last checkpoint` as a *normal, pre-commit* edit. The hook
   never touches tracked files.
2. **Pre-commit recording, not pre-push.** Block the push with a clear
   message instructing the operator to record the waiver line in the spec
   and amend/append it to the commit *before* re-pushing, so the audit
   trail ships inside the pushed commit. (More friction; keeps the trail
   in-spec.)
3. **Stderr-only + commit-message trailer.** Emit the waiver to stderr
   and require it be captured in the commit message trailer at commit
   time (consistent with the M1.5 agent-trailer mechanism). No file
   mutation at all.

Approach 1 is the lightest and most robust to gate ordering; it is the
recommended starting point. The decision is recorded as an addendum to
[ADR 0007](../../decisions/0007_multi_agent_handoff.md) when this story
runs.

## Non-goals

- Do NOT change *when* a waiver is required or *which* paths/deps trigger
  a gate — only *how the audit trail is recorded*.
- Do NOT weaken any gate (PMR / dep / scope / commit-msg).
- Do NOT retroactively rewrite the already-committed audit lines in
  `3C.3` / `3C.8` specs (they are valid history).

## Implementation steps (sketch — refine on promotion)

1. Choose the approach (default: separate untracked log).
2. Refactor `append_audit_line` usage in both gate scripts to target the
   chosen sink; keep the dry-run path.
3. Update `tests/test_check_file_scope.py` +
   `tests/test_check_story_dependencies.py`: assert no tracked file is
   modified on a waived run, and assert the waiver is recorded in the new
   sink.
4. Update `scripts/install_hooks.sh` doc/comments if the hook contract
   changes.
5. Record the decision as an ADR 0007 addendum; note the follow-up
   workflow in `docs/roadmaps/meta1_agent_collaboration.md`.
6. PMR gate dry-run.
